## 3. 测试结果

**ST-LONG-01**（15 分钟，评审后重跑，提交 `2897000`）：**通过**，用时 917.6 s。

| 项 | 结果 |
|---|---|
| 窗口数 | 8,867 个，9.85 Hz；每分钟 584–600 个，全程平稳 |
| 完整性 | 数据库、会话总数、分页的 `GET /windows`、JSON 导出、CSV 导出，全部恰好是窗口 1..N |
| 抽查对账 | 112 个窗口全行一致 |
| 页面 | 只保留最新 500 个 |
| 异常 | 无故障、无重发、无停止面板、无控制台错误 |
| 往返耗时 | 每分钟的中位数在 24–33 ms 之间，p95 在 28–40 ms 之间 |
| 渲染耗时 | 中位数 3 ms |
| 浏览器 JS 堆（经 CDP 读取的真实值） | 在 16.4–29.1 MB 之间来回波动，是垃圾回收造成的锯齿，**没有上升趋势** |
| DOM 节点数 | 1,058–1,418，没有增长 |
| 数据库 | 线性增长到 43.4 MB，约每个窗口 4.9 KB |

**更正**：第一次运行（`5040e9d`）记录的「JS 堆始终 23.1 MB」是**伪迹**，不是测量结果。原因是 Chromium 没有开启精确内存信息，`performance.memory` 是分桶、很少刷新的，15 个样本全部恰好是 23,100,000，所以根本看不出增长。评审指出后，测试改为通过 CDP `Performance.getMetrics` 读取，并重跑了 15 分钟。上表是重跑的数据，第一次运行的证据已被替换。

用变异检验：把导出截断到 500 条，这条测试变红。

**PERF-01**（600 个窗口，预热 20 个，9.8 Hz）：

| 分段 | p50 | p95 | 最大值 |
|---|---|---|---|
| **capture → render** | 28 ms | **39 ms** | 280 ms（仅作参考） |
| 截帧到发送 | 0 ms | 0 ms | — |
| 网络加服务端 | 24 ms | 35 ms | 253 ms |
| 渲染 | 3 ms | 5 ms | 27 ms |

- **≤ 1 s 的目标（按 p95 判定）：达标。**
- **服务端 Server-Timing 各段的中位数**：总计 16.7 ms，其中视觉 8.6、预处理 2.6、遥测 1.1、提交 0.9、融合 0.1 ms。
- **新鲜度敏感性**（用实测的证据年龄计算）：
  - 阈值 2 s 时，0.89% 的遥测窗口会过期（560 个中有 5 个）；
  - 3 s 和 5 s 时都是 0%；
  - 视觉年龄的 p95 是 0.082 s。
  - 遥测年龄在 0–2 s 之间是**回放分段造成的**，不是传感器年龄。

**PERF-02**（四个阶段：正常运行 → 网络丢两次投递 → 后端停机后在同一库上重启并点 Retry → 一个被服务端拒收的 422 请求）：

| 项 | 结果 |
|---|---|
| 逻辑请求 | 211 个 |
| 实际投递 | 216 次：网络层丢弃 2 次，后端停机期间连接失败 3 次；重试编号 2、3 为自动，4 为手动 |
| 服务端 | 存下 210 个窗口，1 条 `input_validation` 故障记录 |
| D1（服务端收到的请求） | 211/211 = **100%** |
| D2（全部逻辑请求） | 211/211 = **100%** |
| 重复的 request_id | 0 |
| 不可用窗口 | 2 个，按 CNT 默认口径计为「已接收」 |

两次停止面板的文字都正确：后端停机时显示「The backend cannot be reached」，422 时显示「The server rejected the request as invalid」。

**G-W6-A 回归门禁**：在最终代码 `2897000` 的全新克隆上运行（ST-COLDSTART-01，`docs/evidence/2026-10-22/coldstart-final/`）：build 通过；pytest **1028 passed / 0 skipped**（1 deselected，即 ST-LONG-01）；vitest 922；tsc 0；eslint 0；启动服务检查通过，没有残留的后台服务。

## 4. 问题与风险

- **已知缺口（记为 Minor）**：浏览器的计时缓冲从来收不到 Server-Timing。Live 循环没有把响应头传给 `TimingInput.serverTiming`，所以 `window.__draLiveTimings` 里的 `server` 字段一直是空。PERF-01 改为从网络层直接读取这个头，数字不受影响。修它要改 `liveLoop.ts`，而这个文件正在回放分支上修改，所以留到两边合并之后再处理。
- **裁定**：PERF-01 以 p95 判定，最大值只作参考，依据是覆盖矩阵增补节。本次最大值 280 ms，也在 1 s 以内。
- **更正**：提交 `4f38cfc` 的提交信息里有 4 个数字取自第一次运行，与已提交的 `perf01.json` 不一致：遥测在 2 s 阈值下的过期比例 1.07%（应为 0.89%）、视觉年龄 p95 0.078 s（应为 0.082 s）、网络 p50 26 ms（应为 24 ms）、渲染 p50 4 ms（应为 3 ms）。提交信息无法修改，本报告与证据 README 一律以 JSON 为准。这是独立评审发现的问题。
- **独立评审**（整分支，审查 84a1891..66327ee）：没有 Critical；5 条 Important 和我上调的 2 条都已修复，每一条都先用测试或复现证明问题存在、再证明修复有效；其余 11 条 Minor 记为暂缓，见 W5 / W6 汇报与账本。
- **测量范围**：只有一台开发机、一种假摄像头图案。目标硬件和真实摄像头上的性能还没有测。
- **E2–E5 runner 没有做**，原因见第 1 节，G-W6-A 里如实标注为未完成。
