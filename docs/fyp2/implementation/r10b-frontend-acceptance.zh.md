# R10-B 验收报告（中文）：前端的遥测 seq 与采集时间、视觉帧元组、payload 约束、文案

## 1. 任务概要

- **编号与名称**：R10-B，R10 的前端部分（R10 v3 + estp5 + 3 个细节，2026-10-16 批准）。
- **实现了什么**：
  - **遥测游标**（接手 Task 9 留下的 `preparedTelemetryAt`）：
    - 按有效监测时间每 2 s 前进一个 `seq`，`seq` 在会话内不封顶，行号 = `seq % 25`。
    - 暂停时冻结。恢复时立即开始一个新观测：`seq + 1`，采集时间就是恢复时刻。
    - 采集时间是算术值：分段基线 + 2000 ms × 段内序号。所以同一个 `seq` 在不同请求里的时间逐字节相同，不再使用发送时刻。
    - 新会话的 `seq` 从 0 开始，重试不会移动游标。
  - **视觉帧元组**：
    - 采集用的 `<video>` 每次触发 rVFC 回调时，立即截帧，并缓存 `{epoch, index: presentedFrames, captured_at, captured_at_source, image}`。推理比相机快时，多个 tick 复用同一个元组，服务端判为 REPEAT。
    - epoch 取摄像头启动时刻的毫秒数，页面刷新后恢复同一会话时仍然单调递增。
    - 有 `captureTime` 时用它作采集时间，否则用回调时刻，并在 `captured_at_source` 里注明来源。
    - 不支持 rVFC，或 1 s 内一次回调都没有，就退回到图像哈希身份。本次摄像头启动期间不会再切回。
  - **payload**：摄像头关闭时不发 `vision_frame`，遥测缺失时不发 `telemetry_seq`，从而避开后端的两条 422 规则。Task 8 的冻结重试语义不变。
  - **文案与分类**：
    - `observation_conflict` 不可重试，停止，文案准确。
    - 手动重试时对账失败，不再显示「已自动重发」。
  - **跨语言契约**：后端测试用前端实际产出的 payload 形状（有帧有遥测、无帧、遥测为 null、回退模式）断言能被接受，违反 422 规则的形状会被拒绝。
- **为什么必要**：只有 R10-A 的后端还不够。Live 的遥测时间戳原来是发送时刻，同一行遥测每次都拿到新的时间戳，所以既无法识别重复，也永远不会过期。视觉没有帧身份，同一帧被画两次就像两个新观测。R10-B 补上之后，R10 和裁定 A 在 Live 路径上才真正生效。

## 4. 问题与风险

- **失败测试**：无。**非预期回归**：无。
- **勘误：R10-A 验收报告中的一句话**。原文写「R10-B 的客户端总是带显式身份」，这不准确。实际规则是：每次摄像头启动内，身份类型不会来回切换；但同一会话里，跨不同的摄像头启动，可能出现「显式 → 回退 → 显式」。评审分析了代码：缓存会在摄像头释放时丢弃，每个新 epoch 都严格更大，被冻结的又只有最新那个请求。所以不存在「在回退帧之后重发旧显式身份」的路径，R10-A 中「混用身份导致 409」的情形不会出现。控制者接受这个范围。
- **Task 10 第 2 部分及 PERF-01 必须考虑的几点**：
  - 遥测的采集时间是时段起点，所以服务端看到的遥测年龄是 0–2000 ms 再加上请求延迟。默认阈值 3 s 时没有问题；但做 2 s 阈值的敏感性测试时，每个时段的尾部会过期，被当作 missing。这个年龄**不是**传感器年龄。
  - 摄像头启动后最多 1 s 内，请求不带图像（not_ready），这不算故障。
  - `captureTime` 没有和回调时钟做健全性对比。如果页面加载后墙钟被回拨，可能导致时间超前 5 s 以上，触发 422 clock_skew 停止。已记为限制。
  - 每次 rVFC 回调都要做一次 drawImage + toDataURL。在合成画布流上中位耗时 2.2 ms；真实摄像头 30 fps 下的开销还没测。
- **外观问题**：提交信息里多出一行 Sonnet 署名，与 R10-A 情况相同。最后一行仍是规定的 Opus 行。
