# Task 7 验收报告（中文）：fault_events —— 失败可观测，且会话删除后仍然保留

## 1. 任务概要

- **编号与名称**：Task 7，`fault_events`（D02 的「持久故障表」）。
- **实现了什么**：
  - 每一次失败的 `POST /infer` 尝试都会**持久记录一行 fault**。记录内容包括：会话、请求 id、尝试序号、出错环节、类别、HTTP 码、是否可重试、详情。
  - 这张表**没有外键**。会话删除后，它的 fault 记录仍然保留、仍可查询。
  - 同一会话里有新记录成功提交后，之前所有 `open` 的 fault 标为 `recovered`，并记下由哪个请求恢复。
  - 新增接口 `GET /api/faults?session_id=…`；`/system-status` 新增 `open_fault_events` 字段。
  - **拆分了模型错误**：模型文件缺失或无法加载 → 503 `models_unavailable`，不可重试；模型运行时出错，或输出非有限、形状不对 → 500 `model_runtime`，可重试。原来这两类都是 503。
  - 数据库写不进去时，fault 写进独立的文件 sink `backend/logs/fault_events.log`（已被 git 忽略），原始异常照常向上抛出，不被掩盖。
- **为什么必要**：D02 要求「连续 3 次失败后停止、可以手动重试、有持久故障表」。在此之前，失败的请求不留任何痕迹，只有成功的记录。客户端也无法区分「重试没用」（模型缺失）和「值得重试」（暂时性运行错误）。
- **行为变化**：
  - 模型运行时出错的 HTTP 码从 503 改为 500。模型缺失的 503 不变，原有两个 503 测试仍然通过。
  - 一路模型运行时出错、另一路正常时，**整个请求失败**（R6 第 5 条，我的默认裁定），不降级成单分支窗口。
  - 其余成功路径的行为不变。

## 4. 问题与风险

- **失败测试**：无。**非预期回归**：无。
- **我的默认裁定，你可以推翻**：一路模型运行时出错、另一路正常时，整个请求失败，丢掉一个窗口。改成降级处理属于产品行为变化，需要你决定。
- **留给 Task 8 的依赖**：
  - 客户端每次投递都**必须**带 `X-Attempt-Index`。不带的话，同一请求的多次失败会因唯一索引被折叠成一行，sink 里仍是每次一行。已写进 Task 8 brief。
  - 500 的响应体随原因不同：`model_runtime` 返回 JSON，存储错误和未知错误返回纯文本。客户端应按状态码分类。
- **已知的小缺口，评审确认危害低，不再修**：
  - 「持锁后的第二次重放检查」确实在持锁之后执行，这一点没有测试钉住。即使把它挪到持锁之前，并发重复请求仍会被后面的唯一索引兜住，只是白做一次推理。
  - 该检查的 409 分支没有单独的测试，结果与兜底路径相同。
- **未做**：`GET /api/faults` 没有分页（最早的记录排在前面，最多 1000 行）；`exhausted` 状态不写入，因为 3 次上限属于客户端。两者留到 Task 8 / Task 10 按需处理。
