- **实现了什么**：
  - **后端判定**：证据年龄超过 `freshness_tolerance_s`（严格大于，3.000 s 仍算 fresh）就判为过期，按 missing 计分。运行时**不再产出 `stale`**。客户端在 `/windows` 声明为 stale 的分支，也按过期处理。
  - **保留原因**：每条新记录的 provenance 里，两路都写 `{modality}_expired` 与 `{modality}_age_s`。年龄按 ROUND_HALF_UP 保留 3 位，最小为 0。时钟超前 5 s 以上返回 422 的规则不变。
  - **EMA**：过期的 vision 不参与平滑。下一个 fresh 帧重新作为起点。
  - **prepared replay**：`age > 3` 由 stale 改为 missing，同样写入四个 provenance 字段。
  - **0.45 档保留**：三份融合实现都保留这一档，用于读取和显示历史 stale 记录。夹具里的 stale 用例标为 legacy，期望值一个没改。
  - **界面**：过期的分支显示为「expired（N s）」，与「missing / No input」区分开。「Latest result is stale」提示保留。
  - **原先钉住错误行为的测试，全部改为断言需求行为**：IT-LIVE-AGE、UT-TIME-06、D13 快照、两条 gap 测试、F1 的 W16（62.5 → 60.0）、Task 8 的 IT-RETRY-STALE。
  - **新增测试**：
    - IT-EXPIRY-REASON：区分「过期」与「没收到输入」；
    - IT-EXPIRY-SENSITIVITY：阈值设为 2、3、5 s 时，分别在边界两侧验证；
    - IT-EXPIRY-NO-STALE：新记录不再出现 stale；
    - 历史 stale 记录仍能正常读取与导出。
- **为什么必要**：D13 是门禁之外唯一没关的 P0。修复前，只有 stale 证据的窗口，0.45 在融合公式的分子和分母里互相抵消，等于没打折。同一会话反复提交 30 天前的旧帧，告警会升到 HIGH_ALERT，这是一个「假的高」。
- **行为变化**：只有过期证据时，窗口为 UNAVAILABLE，四个风险字段为 null，告警计时挂起，**不再能升级到 HIGH_ALERT**。
