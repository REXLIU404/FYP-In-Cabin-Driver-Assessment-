## What green tests do not establish

- Both-missing `computeRiskScore==0` passes the old test but is **INVALID as v2 acceptance**. Independent diagnostic E3-03 observes0/Low/NORMAL+UNAVAILABLE; UT-FUS-ZERO-WEIGHT also fails unavailable oracle. `DIAGNOSTICS` process exits0 because it records observations, not because all requirement checks passed. These are two failed requirement cases, not failures hidden inside the original60-test count.
- Direct provider→expected probabilities in live integration reuses the same model/adapter. It is a useful **wiring** oracle, not independent prediction correctness. Service preprocessing versus separately composed torchvision transform is stronger for preprocessing. Model classification needs labels and frozen holdout.
- Backend FSM fake `now` is meaningful. TS timing tests partly import threshold constants from the implementation; changing both expected boundary and implementation together can mask a requirement drift. The audit diagnostic uses independently fixed2s/10s values.
- Only 3 named FSM severities exist. Five evidence-description categories do not verify a five-state alert design.
- Replay coverage tests use production output categories as data-coverage assertions. That is reasonable for demo fixture coverage, circular if repurposed as proof of correct fusion or classification.
- Source testing gaps: browser hooks/components, API↔UI consistency, fault event persistence, DB failure/recovery, model-run exception, timeout recovery, log completeness/endurance, actual UAT. Schema rejection alone is not full error-handling acceptance.
